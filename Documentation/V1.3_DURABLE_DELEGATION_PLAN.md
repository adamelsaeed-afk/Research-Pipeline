# V1.3 — Durable Delegation: Implementation Plan

Status: fully implemented on branch `V1.3-delegate-repair-instructions-repair` — A (ledger,
limits, validated tables, token telemetry), B (research_mode, research role, revalidation
role, concurrency cap with live registry), D (staleness warnings, recovery procedure, run
states), and C/E (the instruction pass: SKILL.md four-role bounded-dispatch guidance,
long-session export rule, method-disclosure and compound-question rules; intake.md
research-mode and budget questions; delegation.md contract, prohibition, and recovery;
validation_protocol revalidation). Awaiting the owner's commit decision.
Evidence base: the 2026-10 live-test audit findings, documented separately outside this
repository. This plan is self-contained; the skill requires nothing from that archive.

## Goal

Every delegated run's work lands on disk as it is produced. Every run is counted and dated. Every
limit is a user decision enforced before a dispatch launches. Every method choice — new files,
unusual recovery, model substitutions — is disclosed at the checkpoint where it appears.

The fix set in one line: **everything lands on disk, every run is counted, every record is dated,
every method is disclosed.**

## Design rules (non-negotiable for every change below)

1. **Artifacts before labels.** States and counts derive from files on disk, never from the
   agent's belief. A state nothing on disk backs up is not a state.
2. **Append-only over mutable.** The ledger and run records are append-only. No hand-edited
   cumulative status files.
3. **Block, then ask.** Enforcement happens before a dispatch launches, not as a report after.
4. **Nothing new is silent.** New helper files, new tools, and unusual recovery are checkpoint
   disclosures, not implementation details.
5. **Artifact-only recovery.** Recovery reads run directories. Reading any CLI application's
   internal store (SQLite/protobuf) is an ask-first action requiring explicit user approval.
6. **No invented numbers.** Usage telemetry is what tools actually print; absent counters stay
   `unknown`, never converted through an assumed rate.

## Workstreams

### A. Ledger and run limits (scripts/research_dispatch.py, scripts/check_intake.py)

- **A1 — Run ledger.** Append-only `run_ledger.jsonl`, one JSON object per line, written by the
  dispatcher itself. Two lines per run: `launch` (ts, run_id, role, target, cli, model,
  staged_input_bytes, brief_bytes, timeout_s) and `complete` (ts, run_id, exit_code, verdict,
  duration_s, tokens_reported or null). Failed and timed-out runs still get a `complete` line.
  Ledger path: new `--ledger` argument, defaulting to the run directory's parent. Crash during
  write loses at most the current line. No mutable fields anywhere.
- **A2 — Intake branch.** New intake decision `approved_run_counts` (per role: research, validate,
  gap_fill, revalidate), recorded with `user_evidence` exactly like `validation_mode`. Absent
  means unset; the checker treats unset as an open branch, not a default. Answer shape: a JSON
  object mapping role names to nonnegative integer counts. The checker's string-answer rule gains
  exactly one exception: when `approved_run_counts` is answered, the checker validates the object
  structurally — keys must be known delegated-role names (kept in sync with the dispatcher's
  ROLES), values must be nonnegative integers, at least one entry, no other keys — so a typo'd
  role name cannot silently disable a limit. The string rule is unchanged for every other
  decision. What no checker can establish: that the recorded number matches the user's actual
  intent — that layer remains the `user_evidence` fields, bound against later edits by the intake
  digest and enforced by the dispatcher's refusal loop.
- **A3 — Enforcement.** In `run_dispatch`, before staging: count prior ledger entries for the
  role; if the count has reached the approved number, refuse with a notice naming the count and
  the exact intake evidence required to proceed. Mirror the existing `confirmed_target` refusal
  style. Raising a limit requires a new intake entry — the dispatcher cannot be bypassed by a
  flag; the bypass is a renewed user choice.
- **A4 — Failed runs count.** Ledger lines exist for failures; counts include them. A retry is a
  new run.
- **A5 — Telemetry.** Extract token counters from retained stdout when the CLI prints them
  (pattern per CLI, best-effort); absent counters recorded as `null`. Never summed across CLIs
  into one fake unit.
- **Tests:** ledger lines for success/failure/timeout; refusal at the limit; refusal text names
  the evidence path; count includes failures; ledger survives concurrent append from two
  dispatches.

### B. Research mode and delegated roles (scripts/research_dispatch.py, references/delegation.md, references/intake.md)

- **B0 — Research mode as an intake choice.** New decision `research_mode` mirroring the existing
  `validation_mode`: `coordinator` (default — today's behavior, the originating agent researches
  and writes `raw_findings.md`) or `delegated` (a primary-researcher CLI does the research). In
  `delegated` mode the delegation contract covers four roles: researcher, validator, gap filler,
  revalidator; the researcher's CLI target and model are recorded at intake like the validator's.
  **Recommended default: `delegated` whenever external CLIs are configured and pass preflight.**
  If the user still picks `coordinator`, the intake records that they accepted the
  instruction-enforced caveat (C1): coordinator work is discipline-enforced, not code-enforced.
  This formalizes the live test's M025 reassignment, which today has no supported path and forced
  synthetic intake fixtures.
- **B1 — Delegated research role.** The dispatcher supports `--role research` so mode `delegated`
  dispatches through the tool. Input: `questions.md`, whose research questions carry question IDs
  (Q1, Q2, …) recognized by the existing ID machinery. Result contract: `role='research'`,
  `verdict='completed'|'blocked'`, `summary`, `findings=[{id, question_ids, claim, source_urls,
  retrieved, source_date?}]`, `unanswered=[{question_id, reason}]` — findings carry stable IDs
  ending in a digit, valid source locators, and a YYYY-MM-DD retrieval date, under the same
  evidence standard as validate inputs. Coverage check: a completed run must account for every
  input question via findings or `unanswered`; duplicates and unknown IDs fail. A blocked run
  needs no coverage. Research results require attention when blocked or when questions went
  unanswered, and always state that findings require validation before use.
  **Result sizing under the existing 4 MiB contract bound:** a research dispatch returns distilled
  findings with IDs and provenance — never raw page dumps — and realistic per-group outputs are
  tens to hundreds of KB. If a result would not fit, the dispatch scope is too large: split into
  more dispatches (the run limits exist to approve that count) rather than raising the cap; any
  cap change is a deliberate contract decision with tests, never a silent bump. The 4 MiB bound
  governs contract artifacts (result JSON, staged input, parsed streams); checkpoint exports and
  retained raw streams are disk artifacts and are not bound by it.
- **B2 — First-class revalidation.** Revalidation becomes its own role instead of a wrapper-mapped
  validate (`intake_revalidation.json` fabrication in the live test). Default target: a fresh
  session of the confirmed validator CLI (delegation.md already requires each pass to be a
  separate run); a different CLI is used only when the user names one. `confirmed_target` learns
  the revalidator prefix.
- **B3 — Concurrency is settled, not assumed.** When mode `delegated` is chosen, intake also
  settles whether research dispatches run concurrently and how many (the live test's lesson:
  approving eight subjects did not approve eight concurrent sessions). Captured
  in `approved_run_counts.research` and an `approved_concurrency` table (per-role maximum of
  simultaneously in-flight dispatches, minimum 1). The cap is enforced atomically: each dispatch
  reserves a slot under a cross-process lock in an in-flight registry beside the ledger before
  staging anything, a launch beyond the cap is refused (never queued — queueing is the mailbox
  route's job), the slot is released on every exit path, and a crashed dispatch's slot is
  reclaimed by the next dispatch's stale-entry cleanup (the reservation records the dispatch
  process's pid; a dead pid means the slot is free). Unset means serial (cap 1) — parallelism is
  never silently enabled.
- **B3 note — staleness resolution is a re-choice, not a verdict.** When a staleness warning
  fires, the resolution presented to the user is a fresh routing decision, not a true/false
  question: keep the recorded value, adopt what the newer runs used, or choose a different
  target/model entirely — whichever the user wants, recorded with their message as evidence and
  bound by the confirmation hashes. If the chosen routing differs from what the runs used, those
  runs remain exceptions and any model-sensitive work is redone under the new choice. If a run
  is in flight under the previous routing when that choice is made, surface it as a checkpoint
  question — let it finish or stop it — and never stop it automatically.
- **B4 — Retire the workaround surface.** With B0–B2, document that synthetic intake fixtures and
  schema-mapping wrappers are contract violations, not implementation choices.
- **Tests:** five-role arrangement like the live test dispatches every leg through the dispatcher
  with zero fabricated intake files; role/target confirmation for all four delegated roles.

### C. Checkpoint discipline (SKILL.md, references/delegation.md)

- **C1 — Bounded dispatches are the default for every role, research included.** Instruction
  change: in `delegated` mode, research happens as bounded dispatches whose artifacts land in run
  directories by the existing contract. Honest asymmetry to state in the skill: in `coordinator`
  mode the same discipline is instruction-enforced — the coordinator checkpoints its own findings
  as it works — because the dispatcher cannot see the agent's own writing; delegated work is
  code-enforced, coordinator work is discipline-enforced.
- **C2 — Long-session exception.** When a genuinely long interactive session is unavoidable, it is
  permitted only with the export rule attached: the coordinator saves work-in-progress to the run
  directory after each completed unit of work (source read, findings chunk), with an N-minute
  timer as backstop. Export design: individual append-only files, one per completed unit, named by
  timestamp and sequence and never overwritten, so recovery resumes from the newest complete file
  and no single export grows large. A long session's cumulative export size is unbounded by design
  and is made visible instead of capped: each export appends a ledger line (`event: "export"`,
  run_id, ts, bytes), so out-of-dispatcher work is counted like dispatch work. Exports are
  snapshots of another program's state with truncation risk — evidence to review, never a
  completeness guarantee — and container sessions export to the host-mounted shared directory
  (C3), because anything left inside the container is destroyed at teardown.
- **C3 — Container note.** In Docker setups, run directories and ledger paths must be the
  host-mounted shared directory required by delegation.md already. Container teardown destroys
  anything not on the mount — which makes C2 stricter there, not optional. Reuse the existing
  wording style; add no new mount mechanics.
- **Tests:** none (instruction change); cross-reference consistency check in the existing docs
  tests if present.

### D. Freshness, recovery, states (scripts/check_intake.py, scripts/preflight_delegate.py, references/delegation.md)

- **D1 — Staleness detection.** Implemented in `preflight_delegate.py` (the pre-dispatch
  checker) over the artifacts that exist: it compares the intake record's last-write time against
  the ledger's dated run records and warns when the record predates run activity — naming the
  newer record and stating the precedence rule — and warns when runs *newer than the record*
  dispatched a role to a target the record does not confirm (older contradicting runs stay
  silent: a reconfirmed record legitimately outranks its own history). Warnings print to stderr
  and never silently trust; the ledger itself stays fail-closed. Corrupt ledgers refuse the
  check.
- **D2 — Recovery procedure.** Documented in `references/delegation.md` ("Recovering work from
  disk artifacts"): the per-run artifact inventory, the recovery order (states → retained
  streams → newest checkpoint export), the rule that recovered material is recorded as a new
  ledger event and a retry is a new run, and the prohibition: a CLI application's internal store
  is an ask-first method with stated scope — artifact-only recovery is the standard, and the
  database was only ever the fallback when no artifacts existed.
- **Tests:** stale-field warning triggers; precedence resolution; state derivation from ledger
  sequences including orphan (launch without complete).

### E. Instruction changes (SKILL.md, references/intake.md)

- **E1 — Helper-file disclosure rule.** At the first checkpoint where creating new executable
  files becomes necessary: state the language, the expected file count, and the existing-tools
  inventory; prefer direct dispatcher calls before any wrapper. (Live test: 14 files over ~10
  hours, first disclosure at M078.)
- **E2 — Budget/usage checkpoint.** The intake decision map gains the `approved_run_counts`
  branch (A2) plus the rule: state the expected run count before exceeding an approved one; with
  no ceiling agreed, cumulative usage is reported at every checkpoint.
- **E3 — Compound-question rule (fix item 10).** See "Item 10 explained" below.
- **E4 — Cross-references.** Update delegation.md and validation_protocol.md wording that
  conflicts (e.g., "no resume or continuation option" stays true for the dispatcher but the
  long-session exception and its export rule are documented beside it).

## Item 10 explained (E3, for the implementing agent)

Two documented failures motivate this rule, both communication, not code:

1. **M078–M079.** The user asked three things at once: modifying the skill? what are you doing?
   what are these .py files? The assistant answered only the narrowest literal part ("No, I have
   not modified the `SKILL.md` files"). Literally true, but the user's evident concern — the
   visible file sprawl — went unanswered, and the "No" could be read as denying the files too.
2. **The M086 promise.** "I will … continue … without adding new helper scripts" was honored
   literally while existing helpers were edited and code kept running. The promise covered the
   letter of the complaint (file count), not the concern (unexplained complexity), and never
   stated what would still happen.

Add to SKILL.md a short section (working title: "Answering user concerns") with four requirements:

- A multi-part question gets **every part answered, explicitly, in order** — never one part.
- **Lead with the part the user emphasized** (repeated punctuation, "important question") — that
  emphasis marks the actual concern.
- If the literal question and the evident concern differ, **say both**: "I have not modified the
  skill's files, and I have created 14 new helper files; here is why." A literal-truth answer that
  dodges the concern is a failed answer.
- Any commitment ("no new files") must **state what will still happen** (existing files will be
  edited; code will run) so its scope is unambiguous.

This is instruction-level because it governs agent behavior; the mechanical support is E1's
disclosure checkpoints, which force the conversations this rule governs.

## Sequencing

1. **A** (ledger + limits) — self-contained, fully testable, immediately valuable.
2. **B** (roles) — removes the workaround surface before C/E formalize the discipline.
3. **D** (staleness, recovery, states) — builds on the ledger existing.
4. **C + E** (instructions) — after the mechanics exist so instructions describe real behavior.

## Acceptance criteria

- A dispatch beyond the approved count refuses before launch, naming the count and the required
  user evidence; a new intake entry with evidence unblocks it.
- Every dispatch — success, failure, timeout — leaves ledger lines; run counts per role are
  derivable by counting lines; no hand-maintained totals exist.
- A run killed mid-flight leaves retained streams on disk, and the recovery document restores
  material from the run directory alone.
- A status file older than newer dated run records triggers a checker warning naming the newer
  record.
- A `delegated` research-mode arrangement like the live test's (researcher, validator, gap filler,
  revalidator) dispatches every leg through the dispatcher with zero fabricated intake files, and
  `coordinator` mode behaves exactly as the skill does today.
- All existing tests pass; each behavior above has a test.
- No new runtime dependencies; Windows (Git Bash) compatible; the security posture (argument
  arrays, `shell=False`, 4 MiB bounds, intake contract shape) is unchanged.

## Constraints

- Do not weaken existing contract checks while adding roles; extend them.
- Do not replace the mailbox route; the ledger and limits apply to both routes where mechanics
  allow, and the plan documents any gap instead of silently diverging.
- Instruction edits follow the repo's writing-for-agents conventions: one entry point, focused
  documents, explicit limits of what each check can and cannot prove.
